# Assurance integration

Assurance is an explicit addition to the focused workflow, not a new lifecycle command or a default behavior change. The visible journey remains `init → spec → plan → execute → ship`; projects without an adopted manifest retain existing plan identity and legacy behavior. Promotion is a later explicit decision, not an automatic consequence of local evidence.

## Adoption and authority

`plan approve --assurance <yaml-file>` validates and adopts a reviewed manifest in a fresh approval epoch. Reapproval without the option preserves adoption; replacing the manifest requires the option. `plan approve --assurance-off` removes it through a fresh approval. The approval binds the manifest digest, plan fingerprint, approval/spec IDs, source baseline, and native host identity when validators are declared. A missing or mismatched sidecar blocks until reapproval. `adapter-default` permits existing adapters but explicitly does not enforce information flow.

The strict, bounded v1 records include:

| Record | Schema identifier | Purpose |
| --- | --- | --- |
| Assurance plan | `legion-cli-assurance-plan/v1` | Security policy, knowledge units, validators and declared delivery artifacts. |
| Assurance approval | `legion-cli-assurance-approval/v1` | Approval/manifest/plan identity, host identity and source baseline. |
| Check evidence | `legion-cli-check-evidence/v1` | Input identities/digest, reuse key, module/runtime/configuration, output and execution/reuse lineage. |
| Assurance execution | `legion-cli-assurance-execution/v1` | Product/environment fingerprints, checks, policy and trace statuses, aggregate result. |
| File provenance | `legion-cli-file-provenance/v1` | File digest, label, producer and recording time. |
| Governance authority | `legion-cli-action-approval/v2`, `legion-cli-http-run-authority/v2`, `legion-cli-http-governed-checkpoint/v3` | Exact approved governed effects and resumable HTTP state, with separate bootstrap and program provider-call ledgers. |
| Governance trace | `legion-cli-governance-projection/v1`, `legion-cli-governance-frame/v1`, `legion-cli-governance-head/v1`, `legion-cli-governance-trace/v1`, `legion-cli-governance-epochs/v1` | State projection, approval-bound transition chain, and the cross-epoch anchor. |
| Delivery | `legion-cli-delivery-snapshot/v1`, `legion-cli-delivery-manifest/v1`, `legion-cli-delivery-trust/v1`, `legion-cli-delivery-predicate/v1`, `legion-cli-delivery-outcome/v1`, `legion-cli-delivery-export/v1` | Frozen delivery, inventory, trust policy, public statement projection, outcome and export attempt. |
| Component protocol | `legion-cli-component-request/v1`, `legion-cli-component-invocation/v1`, `legion-cli-validator-output/v1`, `legion-cli-native-host-manifest/v1` | Bounded component request/invocation, result and packaged host inventory. |

These are strict versioned schemas, not proof that their claims are true. IDs, digests and model/policy/runtime identities make records linkable; they do not authenticate the human behind a local actor label. Control records are engine-owned and protected; indexes are projections, not another authority store.

## Information-flow limits

An adopted security policy declares exact source paths classified `public`, `workspace`, or `sealed` (unclassified input defaults to sealed), exact sinks with permitted classifications, named transformations, task read-path contracts, and external-call grants. A grant binds tool, sink, effect, authority arguments and non-overlapping data-only JSON pointers. In `information-flow` mode every task must have explicit reads and transformation references; unsupported adapter/mode combinations are blocked before spawn. HTTP governed execution uses distinct authority/checkpoint records rather than changing the legacy checkpoint format. Ordinary adapters, approved argv checks, labeling, sandboxing, and an honest custom validator do not together establish universal noninterference or prompt-injection immunity. Filesystem race resistance and copy-jail behavior are bounded mechanisms, not a claim of hermetic execution.

A governed HTTP-MCP call sends exactly the granted authority arguments plus each data value at its declared pointer. Approval refuses a pointer that lands on, inside or above an authority value (data may only add new keys to authority objects); the engine assembles the final arguments from the authority, refuses any overlap as `policy-denied` before admission, validates them against the tool input schema, and binds their digest (`argumentsDigest`) into the `http-mcp` request digest that the operator approval attests. Dispatch transmits those assembled arguments unchanged.

## Knowledge and evidence reuse

A knowledge unit binds a reviewed statement to a source path and, optionally, a qualified TypeScript/JavaScript selector (`function`, `class`, `method`, `type`, `interface`, or `variable`), acceptance/task IDs, dependencies and check links. Missing, ambiguous, renamed or unparsable bindings are unknown; dependencies must be declared and acyclic. Selectors use the pinned TypeScript 5.8.3 syntax parser. A selector-free unit observes whole-file bytes, not inferred semantics.

A component receipt can be reused only when its prior result passed and its approval epoch, manifest/check/configuration, supplied canonical packet, input-unit closure and modes, parser, module hash, native runtime/settings and platform identity match. Syntax-projection inputs can permit reuse after syntax-irrelevant edits when the exact projection is unchanged; raw-file inputs bind bytes, so any byte change invalidates reuse. Declared dependencies are authored input declarations, not proof of complete runtime reads. Product fingerprints still cover the whole product and guard execution; edits can stale aggregate review and manual acceptance even when an individual component receipt remains reusable. Failures remain blocked absent explicit retry. Admission failure has no guest packet digest and is not a reusable execution.

## Model and trace scope

Two pinned Quint 0.33.0 models (Apalache 0.62.1) bound the governance claims; neither is a model of the whole implementation. `models/governance.qnt` models public `LegionEngine` operations in an adopted three-task project: approval epochs, control mode, task amendment (including an overlap refusal), atomic `executeWorkflow` with serial or two-wide batches, review failure and explicit retry, unchanged failed stages, unblock, undo, acceptance, ship refusals (stale approval, not ready, changed preview), PR-failure rollback, confirmed shipment, a SIGKILL interruption during a held provider request followed by crash recovery, and abandon. `scripts/replay-governance-itf.mjs` replays its fixed-seed traces through those public calls in git-initialised, assurance-adopted projects; the loopback provider's review verdict is a deterministic stimulus, and after every ship action and at the end of each trace `inspectGovernanceTrace` must report every visited approval epoch `valid` with no semantic violations. `models/governance-boundaries.qnt` models one governance boundary per action of the frame vocabulary over the abstract projection (three tasks with fixed overlapping writes, approval, claim, integration/component/review, acceptance, ship preview/confirmation and the explicit-retry marker), with guards equal to the semantic validator's rules. `scripts/check-governance-boundaries.mjs` maps its traces to schema-valid hash-chained frames, requires `validateGovernanceFrames` to accept every trace, and appends one synthetic violating step per counterexample class (stale acceptance, overlapping contracts, advisory execution, duplicate claim, implicit retry, changed preview, rollback with completion) that must be rejected with exactly its code. Model checking, conformance and replay complement tests but cannot prove all executions or implementation correctness.

Governance frames record begin/end boundaries, action, correlation, before/after projections, outcome (`success`, `failed`, `incomplete`, or `refused` for a refusal that left state unchanged), explicit-retry marker, model identity, timestamp and chained digest, with an approval-bound head. Traces are `valid`, `incomplete`, `invalid`, or explicitly `not-adopted`. A begun operation lacking its matching end, write failure, stale/orphan head or interrupted mutation cannot be upgraded to valid by inference: current-epoch validation blocks assured ship/export. Only `failed` and `incomplete` outcomes block later operations. Beyond chain integrity, every read and reconciliation applies the shared semantic validator (`validateGovernanceFrames`): advisory execution, a replaced live claim, overlapping active write scopes, completion or shipment without passed checks, use of stale approval or acceptance authority, a rerun of failed checks without explicit retry, a confirmation or completion that changes the prepared preview, a rollback that still claims delivery, an illegal phase or task transition, or a refusal that changed state each make the trace `invalid` with that violation code. Reapproval begins a fresh authority baseline without deleting history; `.legion-cli/audit/governance/epochs.json` anchors the epoch sequence as a digest chain (`sha256("legion-cli-governance-epoch/v1\n" + canonical entry)`), and a malformed anchor fails closed. A completed delivery snapshot freezes its trace; its completed trace must extend the frozen trace consistently.

## Delivery, predicate and trust

Delivery snapshots freeze product inventory, declared artifact digests, evidence, trace and predicate. Export operates by snapshot ID and does not recapture current project state. The manifest identifies exactly five members in canonical path order (`artifacts.json`, `evidence.json`, `predicate.json`, `product.json`, `trace.json`), each bound by digest and size; its SHA-256 is the in-toto subject digest for `manifest.json`. Scope is `git-index` or `host-native-product`; Gitlinks describe only the referenced commit. Bundles contain metadata and digests, not product bytes. Declared artifact entries identify exact paths and content digests that can be checked against independently supplied files. Shipment side effects and delivery-record finalization are reported separately: a pending snapshot is never treated as a completed bundle. `ship export` may finish only from immutable prepared facts plus a durable matching outcome and, for adopted delivery, a successful trace; without those records it refuses rather than rerun ship or infer success from the current checkout.

The in-toto Statement v1 predicate type is:

`https://github.com/9thLevelSoftware/legion-cli/blob/main/docs/design/assurance-integration.md#delivery-v1`

Its strict `legion-cli-delivery-predicate/v1` projection contains UUID tokens for confirmation, approval/spec, task/acceptance/check/profile/model/host identities as applicable; digests, fixed enums/statuses and normalized timestamps. The token-to-local-ID mapping stays in the protected snapshot, not the public predicate. It excludes authored text and arbitrary local names, but is not anonymous: digests, timing, counts and signer certificates can correlate or enable dictionary inference. The local bundle inventory can expose potentially confidential relative filenames. Operators must inspect the exact public predicate and explicitly consent before any public CI attestation; consent is not inferred from local signing or ship confirmation. GitHub attestation publishes the manifest subject digest and full predicate to GitHub/transparency infrastructure. It is optional and not performed merely by these commands.

`ship sign <bundle> --key <path>` locally signs the in-toto statement using Ed25519 DSSE PAE and an external PKCS8 key. Keys must remain outside the project/bundle; key IDs are hints, not trust. No key generation, network trust fetch or automatic signing is implied. `ship verify <bundle>` is stateless: default `--require integrity`; `--require local-key` or `--require ci-oidc` demands that exact trust mode. `--trust-policy` supplies external pinned SPKI keys and/or constrained CI identity/root policy; `--source`, `--artifacts` and `--expect-approval` independently check supplied content/claims. Integrity, authenticity, supplied content and self-reported claims are reported distinctly. Offline verification cannot learn later certificate revocations; trust roots and identity constraints must be provisioned out of band. A valid signature authenticates signed bytes under that policy, not the correctness of reported checks, human approval or build provenance; this is not a SLSA claim.

`ship export` and `ship verify` print `Public predicate SHA-256: <hex> (predicate.json)`, the digest of the exact predicate bytes; the verification report carries it as `predicate.sha256` (null when that member is invalid). The reusable `.github/workflows/delivery-attest.yml` binds consent to those bytes: its required `predicate-sha256` input must equal the bundle's predicate digest or the workflow fails before attesting. `bundle-run-id` selects a bundle uploaded by an earlier run of the same repository. The attest job also composes `ci.sigstore.json` into the full verified bundle and retains it as the `attested-delivery-bundle` artifact for offline `ship verify --require ci-oidc`.

Model evidence: both models pass Apalache 0.62.1 bounded Safety checking through 20 steps (the boundary model checks invariants once per step via `models/governance-boundaries.apalache.json`; the bound is unchanged), and the fixed-seed (20261002) corpus of 1,000 40-transition boundary traces is accepted by `validateGovernanceFrames` while all 7,000 appended counterexamples are rejected with their exact codes. CI runs the public-operation replay over the complete 1,000-trace corpus in eight shards. The public model abstracts `executeWorkflow` and `ship` as atomic calls and does not model information-flow execution, component validators, global recovery, per-task compaction or interrupted-verification recovery. Public GitHub signing/attestation and the integrated acceptance groups are evidenced separately; generated traces and schema support are not completion of those gates.

## Component boundary and platform availability

The packaged Wasmtime 49.0.2 host uses ABI `legion-validator/v1`, export `validate(string) -> string`, a fresh invocation, and an empty linker. No ambient WASI filesystem, network, environment, process, clock or random imports are supplied. Host-provided immutable inputs contain only declared raw files, knowledge projections/dependency closure and configuration. The framed request caps component bytes at 16 MiB, input at 8 MiB and header at 16 KiB; guest result is capped at 1 MiB, fuel at 20 million, stack at 1 MiB, instances at 32, memories at four × 64 MiB, tables at sixteen × 100,000 elements, with a 20-second parent deadline including compilation. Native-process containment is separately probed before parsing/compilation: Windows Job Object committed limit; Unix address-space limit of startup virtual size plus 2 GiB (not an RSS bound). Failure to establish an effective boundary reports unavailable, with no PATH/download fallback. The isolation limits guest authority; it does not make a validator correct or the engine immune to hostile same-user modification.

With the pinned json-contract guest at ~14 instructions per input byte, the 20 million fuel budget bounds practical validated input to roughly 1.4 MiB; beyond that the check reports unavailable (fail closed) rather than passing. The native release smoke records both sides: a 1 MiB input passes and a 2 MiB input is refused at the guest resource bound.

The committed `json-contract.wasm` and its `SKILL.md` pin are the `x86_64-unknown-linux-gnu` CI build. The guest build remaps the checkout and Cargo home out of embedded panic locations so that Linux builds of the pinned toolchain are intended to reproduce the same bytes regardless of checkout path or user; the CI gate (`git diff --exit-code extensions/json-contract` on that target) enforces this for the CI builder only, and cross-host Linux reproduction has not been independently verified. Windows builds embed backslash-separated relative paths and therefore produce a different, unpinned guest; the other native jobs run a "Restore committed guest component" step after building, before testing.

Platform evidence comes from CI on PR #128: Linux (bwrap), Linux Docker, Windows and macOS (seatbelt) suites, all seven native-target smokes plus release assembly, the installed information-flow assurance smoke (bwrap) and the sharded engine replay. The macOS seatbelt enforcement test and the bwrap-gated governed engine tests run only in CI; local Windows evidence does not cover them. Native target manifests/artifacts require target-specific smoke evidence, and local-target coverage is not complete release coverage.
