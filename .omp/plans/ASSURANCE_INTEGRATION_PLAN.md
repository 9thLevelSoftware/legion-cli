# Evidence-governed engineering integration

## Context
The user requests collection and review of the referenced research, followed by a design, development and implementation plan integrating all five identified enhancements: information-flow-governed actions; executable knowledge and sound evidence reuse; model-checked governance and trace validation; independently verifiable delivery bundles; and capability-limited WASI validators. Retain Legion CLI's five-command lifecycle and current TypeScript/Node architecture. The completed twelve-worker whole-product fingerprint optimization is existing infrastructure, not implementation of these five enhancements.

## Assumptions & contingencies
- User-selected rollout: opt-in, then promote. Existing projects and their current adapters continue unchanged until explicit adoption; promotion requires the acceptance gates specified in this plan, not an automatic future cutover.
- User-selected signing posture: local-first, with CI signing optional. Offline verification must not depend on a transparency service; no signing/network disclosure happens without an explicit operator action.
- User-selected WASI delivery: package a small native Wasmtime host for supported OS/architectures rather than require an operator-installed runtime or source build. Rust is limited to the validator subsystem (host, pure guest and dev-only component builder); the CLI and workflow engine remain TypeScript/Node.
- Native host acceptance includes a checked OS memory boundary before untrusted compilation, not only guest fuel/memory. Windows uses a Job Object; Linux/current Darwin use address-space limits with an enforcement probe. A platform/kernel unable to establish that boundary reports the concrete prerequisite and does not execute untrusted components; the ordinary CLI stays available. Existing general macOS CI remains best-effort, but advertised native release artifacts require their specific smoke evidence.

## Research findings recorded during planning
- Reviewed local://technology-edge-research.md, including primary-source links and completed fingerprint experiment results. Requirement/evidence graphs and signed agent provenance have direct prior art; no world-first claim is supported.
- Existing local://repository-guidelines-plan.md is an unrelated documentation plan and is retained unchanged.
- Primary-source review confirms that CaMeL requires actual separation of trusted control and untrusted data, not labels added to a shared model conversation. ECK's small Python evaluation does not establish complete dependency discovery; selective evidence reuse must be bounded by enforceable inputs. AgentSpec motivates finite deterministic policies, not executable model-authored rules.
- Repository discovery confirms that HTTP can intercept individual tools but vendor CLI adapters cannot; file ownership contracts are not read sets; existing map extraction is regex-based; integration evidence currently requires the whole-product fingerprint; and ordinary audit records are best-effort, not a complete transition log. Existing receipts and adapters must retain their current behavior when assurance is not adopted.
- Wasmtime's capability boundary depends on imports actually provided by the host. The packaged validator host will expose only a typed input/output ABI with no ambient WASI filesystem, network, clock, random, environment or process imports. This makes a bounded complete input closure enforceable and avoids Windows command-line limits.
- Signing review found that current Sigstore JS 5.0.0 requires a newer Node floor than Legion's Node 22 contract. Retain the Node floor; use Node's Ed25519 for local DSSE signatures and optional official GitHub attestation tooling with explicit trust roots and identity constraints for CI. Signed predicates and local actor strings do not establish correctness or authenticated human approval.
- Primary-source links and specific verification commitments will remain in this canonical plan. All work so far is read-only discovery and session-local planning; implementation, builds, tests, installations and system changes are not authorized in this session.

## Approach
### 1. Establish the approval-bound assurance contract
Implement assurance as an explicitly adopted focused-workflow contract, not a sixth lifecycle command, a new agent adapter or a second database authority. Add `plan approve --assurance <yaml-file>` and `PlanApprovalOptions.assuranceManifestPath?: string`. Approval imports and validates the draft, persists an immutable engine-owned copy at proposed `.legion-cli/workflow/assurance.yaml`, and binds its digest into `createWorkflowPlanSnapshot` using an `assuranceFingerprint?: string` input. Omit that fingerprint property entirely when no assurance is adopted so existing approval hashes remain unchanged. Reapproval without the flag preserves the adopted manifest; replacement requires the flag, and `--assurance-off` explicitly removes adoption through a fresh approval epoch. Reject simultaneous on/off options.

Keep current strict v1 plan, workflow and acceptance receipts intact. Add strict versioned sidecar schemas, their `SCHEMA_VERSION` entries, public schema exports and JSON-schema emission registrations: `legion-cli-assurance-plan/v1`, `legion-cli-assurance-approval/v1`, `legion-cli-check-evidence/v1`, `legion-cli-assurance-execution/v1`, `legion-cli-governance-frame/v1`, `legion-cli-delivery-snapshot/v1`, `legion-cli-delivery-manifest/v1` and `legion-cli-delivery-trust/v1`. No legacy receipt aliases, speculative automatic migrations or SQLite truth store are needed. Existing SQLite/map/wiki indexes remain disposable projections.
Also emit strict schemas for `legion-cli-action-approval/v1`, `legion-cli-http-governed-checkpoint/v1`, `legion-cli-component-request/v1`, `legion-cli-validator-output/v1`, `legion-cli-native-host-manifest/v1` and `legion-cli-delivery-predicate/v1`. New authority records reject unknown keys; configurable JSON data is explicitly confined to its `configuration`/data field. New knowledge/check/transformation IDs follow the existing extension-ID syntax `^[a-z][a-z0-9-]{0,63}$`; opaque pre-existing approval/run IDs become SHA-256 directory names instead of being interpolated into paths. All records validate before persistence and again before consume/recovery. Reuse the existing `legion-cli-extension-evidence/v1` envelope for standalone extension output, while the component ABI output is separately strict.
Add strict `legion-cli-file-provenance/v1` and `legion-cli-http-run-authority/v1` schemas/exports/emission entries for the persistent label and protected program authority below. Standalone component output `checkId` equals the requested extension check ID; the host maps it to the approved project check ID when writing an assurance receipt. No module-provided ID selects a receipt path.
Emit strict proposed `legion-cli-component-invocation/v1` for standalone execution: `{schemaVersion, checks:[{id,configuration,files}]}`. Require 1–256 unique lower-case check IDs, object-valued JSON configuration, 1–256 distinct normalized product-relative file paths per check, maximum depth 32 and a 1 MiB invocation-file cap. Check IDs must equal the component manifest's required-check set; source bytes cannot be embedded in this control document. This is an operator-selected raw-file invocation, not an approved plan or causal-reuse receipt; knowledge-unit inputs remain available through the approved assurance workflow.

The assurance manifest contains:
- `specId`; `security.mode: information-flow | adapter-default`; an exact source-path classification table (`public | workspace | sealed`, default **sealed** for an unclassified source); exact sink IDs/origins and their permitted classifications; per-task explicit read paths and named transformation instructions; and enumerated external-call grants with fixed names/authority arguments and designated data-only JSON pointers. Writes derive from the approved task/artifact contract rather than introduce a second ownership grant.
- `knowledge[]`: stable `id`, human-reviewed `statement`, `source.path`, optional TS/JS selector `{kind, qualifiedName}`, `acceptanceIds`, `taskIds`, `dependsOn` and `checkIds`. Selector kinds are `function | class | method | type | interface | variable`; missing/ambiguous selectors never silently bind a different declaration.
- `validators[]`: stable project `id`, pinned `extensionRef`, `extensionCheckId`, `componentSha256`, `inputUnitIds`, `inputFiles`, `acceptanceIds` and JSON `configuration`. `extensionCheckId` must name one declared extension `requiredChecks` entry; project IDs may differ and are the receipt/cache namespace. Standalone `skills run` invokes each required extension check exactly once; an assurance validator invokes its named check and rejects any other returned ID. All references resolve within this approved contract; duplicate IDs, cycles, traversal, conflicting labels, undeclared criteria/tasks or a check without a requirement link fail approval.
- `delivery.artifacts[]`: logical name plus exact project-relative regular-file path. No globs, automatic directory traversal, implicit code/log inclusion or signing keys.

Proposed `.legion-cli/workflow/assurance-approval.yaml` binds the primary `approvalId`, `specId`, `planFingerprint`, manifest digest and packaged host identity. Persist the manifest, primary receipt and sidecar under the existing store lock; write the sidecar last. Missing/mismatched partial writes invalidate assurance and require reapproval rather than infer success. Reapproval invalidates old check, acceptance, policy-release and trace authority. Unsupported security mode/adapter combinations fail before spawn; `adapter-default` permits vendor adapters but is visibly reported as **information-flow not enforced**, never full assurance.
Register **every new authority record**, including assurance manifest/approval, file provenance, check/execution receipts, action approvals, governed authority/checkpoint, governance frames/head, delivery snapshots/outcomes/export records and raw protected logs, in the existing canonical engine-owned path protections. Approval rejects overlapping model/task/extension read/write grants; host admission, sandbox staging and copy-out independently reject protected-path aliases. Only engine writers and explicit operator inspection/export APIs access them. In information-flow mode, also exclude these records and live installed-engine files from argv sandbox visibility/writes; an unenforced/copy-only jail does not gain a tamper-resistance claim. `adapter-default` preserves its legacy adapter boundary and must not advertise these application-level checks as hardened OS isolation.

Extract the existing private sorted-object JSON serialization in `packages/design-system/src/integrity.ts` into a shared `canonicalJson` helper in persist and migrate that existing caller without changing its integrity-field omission or existing manifest bytes. Validate finite JSON values before serialization, preserve array order and sort object keys with the existing UTF-16 ordering, not locale-dependent comparison. New identities use SHA-256 over a versioned domain separator plus canonical bytes; existing workflow fingerprints retain their current algorithm.

### 2. Deliver the packaged capability-limited component runtime
Add a proposed Rust helper under `packages/sandbox/native/` because the current sandbox supplies OS command jails, not a component-model host. Pin `wasmtime = =49.0.2`, Rust toolchain `1.96.0` and commit `Cargo.lock`. Enable only `std`, `runtime`, `cranelift` and `component-model`; do not link `wasmtime-wasi`, WASI HTTP, NN, sockets or plugin-native libraries.

The proposed WIT world exports exactly `validate: func(input: string) -> string`. Each invocation starts a fresh process/Engine/Store, loads raw component bytes with safe `Component::new` (never native/AOT deserialization), creates an **empty** component `Linker`, and obtains the checked string-to-string export. Wasmtime 49.0.2 performs post-return automatically. Components requiring any host import fail instantiation. File access is replaced by host-supplied immutable input data: no ambient filesystem/preopens, environment, process execution, network, clock or random capability exists in the guest.

Node snapshots only approved files/units/resources, rejects symlink/junction escapes, and supplies a canonical UTF-8 JSON packet: version, project check ID, extension check ID, acceptance/unit IDs, configuration and sorted input records. Raw file records use `{path, kind, mode, sha256, encoding: utf8|base64, content}`; invalid UTF-8 requires base64 instead of lossy decoding, and missing files are explicit. Unit records use `{unitId,path,selector,syntaxDigest,syntaxProjection}`; full-file byte digests are retained as observation metadata but not smuggled into a syntax-only reuse key. All values actually exposed to the guest belong to the input digest.
Use a framed stdin protocol: 4-byte big-endian header length (maximum 16 KiB), strict request header with ABI, module SHA-256, exact component/input byte lengths and fixed limits, then raw component bytes and canonical input bytes, followed by EOF. Cap component bytes at 16 MiB and input bytes at 8 MiB; reject short/trailing data and digest/UTF-8 mismatch. This avoids base64 module inflation, duplicate JSON copies and mutable guest-selected paths. The helper returns strict `legion-cli-validator-output/v1` `{schemaVersion,checkId,status,observations,recommendations?}`: the exact requested extension check ID; `status: passed|failed`; up to 256 unique observations `{id,status:passed|failed|error,code,detail?}` with lower-case IDs/codes and detail capped at 4 KiB; optional up to 32 recommendations `{title,priority?,type?,detail?}` with title 1–256 characters, `priority:P0|P1|P2`, `type:feature|fix|bug` and detail capped at 4 KiB. The entire result is capped at 1 MiB, and every record rejects extra fields. Native failures become host-generated `unavailable`, not a guest assertion of availability. Proposed `runComponentValidator(input, options): Promise<ComponentValidationResult>` lives in sandbox and returns status plus module/runtime/input identities. Malformed/mismatched output, timeout or resource exhaustion never passes; strip terminal-control sequences from displayed untrusted observation/recommendation strings.

Use an 8 MiB **validator input** cap (separate from the 16 MiB component and 16 KiB framing header), 1 MiB guest-result cap, 20 million fuel, 1 MiB Wasm stack, at most 32 instances, 4 linear memories of at most 64 MiB each (256 MiB aggregate guest-memory ceiling), 16 tables of at most 100,000 elements each, and a 20-second parent process deadline including compilation. Attach Store limits and fuel before instantiation, disable threads/shared memory, canonicalize NaNs and make relaxed SIMD deterministic. These guest bounds are distinct from native-process containment. Store/request IDs, wall-clock timestamps and process timing are not visible to the component. A timeout/resource failure is not reusable.
Before reading the component request or creating its Engine, the native helper establishes a 2 GiB committed-process limit in a Windows Job Object, or a hard Unix `RLIMIT_AS` ceiling of startup virtual size plus 2 GiB. Record the different budget kinds honestly; the Unix setting is not a 2 GiB RSS claim. Verify the limit is effective with a no-touch mapping/allocation probe that must fail beyond the ceiling; API success without actual enforcement is insufficient. Refuse execution if limit setup/probe fails. Configure Wasmtime memory reservation to 64 MiB per linear memory, 64 KiB guards and zero extra reservation for growth so its default multi-GiB reservations do not defeat the boundary. Stream stdout/stderr with hard 1 MiB caps and terminate immediately on overflow. Malicious native compilation/allocation is bounded before guest Store limits apply; test parent survival. Current Darwin enforcement is grounded in [XNU's RLIMIT_AS branch](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/kern_resource.c), not old archived manuals; Windows limits follow [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects).

Extend `ExtensionManifest` with an optional typed runtime `{kind: wasi-component, abi: legion-validator/v1, component: assets/<relative>.wasm, sha256}`. The legacy absent-runtime branch remains its governed HTTP extension job. The component branch is selected **before** adapter resolution, uses existing resource/pin/minisign verification, requires no model, honors only declared read inputs, rejects command/product-write permissions and host-writes the existing extension evidence/recommendation artifacts into the extension run directory. Return exactly the requested required-check IDs once each; reject extras and mismatches. The component cannot choose evidence paths or mutate the product. Preserve the existing CLI's recommendation-to-normal-ticket conversion, never direct execution from a recommendation. `skills run <extension-ref>` invokes either concrete runtime; it is not an AdapterId or an engine SkillId.
Standalone `skills run <extension-ref> --validator-input <json-file>` is a **new advanced option**: current `skills run` only accepts `--profile` and has no validator configuration/source selection. Require the invocation file for component runtimes, reject it for the legacy runtime, and reject `--profile` for components instead of silently ignoring it. Thread a proposed optional `componentInvocation` argument through `runSkillsRun`/`runGovernedExtension`; validate both the document and each path against manifest `permissions.read`, protected control paths and canonical jail containment. Node reads and snapshots the named actual repository files; standalone project check IDs equal their extension IDs and acceptance/unit IDs are empty. Assurance callers instead use their approved per-project check mapping and declared file/unit inputs; they assert only those selected declared checks, not unexecuted module checks.
The established `ExtensionEvidence` is runner-local, explicitly validated, **not** a schema-package strict Zod record. Preserve its legacy parsing; adapt a validated component result to `{id:extensionCheckId,status,detail:canonicalJson(observations)}` inside its current evidence envelope. Write optional bounded recommendations in the existing separate `{recommendations:[...]}` artifact format. Keep `runSkillsRun`'s `engine.fileTicket({title,type,priority,notes})` conversion unchanged; module strings are labeled data, never commands/authority or automatic execution. JSON-contract emits at most 32 deterministic failure suggestions (`bug`, `P2`, assertion-ID title), none on pass. Source anchors read: `packages/cli/src/cli.ts:890-896`, `packages/cli/src/skills.ts:304-353`, `packages/agents/src/extension-run.ts:18-46,76-145,202-215`, `packages/agents/src/extensions.ts:38-53,127-212`.

Build seven native targets: Windows x64 MSVC; Linux x64/arm64 GNU and musl; macOS x64/arm64. Package their binaries and a version/ABI/target/SHA-256 manifest inside the existing allowlisted sandbox package's `dist/native/`; do not add platform npm packages or publish the private root. Native release jobs assemble these artifacts before the existing v-tag-only publisher runs, and prepublish validation rejects missing/hash-mismatched binaries. Normal TS development builds do not require Rust unless testing/building this host. Resolve the host only from the installed package, check target/ABI/hash before launch, and never auto-download or use a PATH substitute. Unsupported targets fail assurance adoption when component checks are required, while ordinary CLI behavior remains available. GNU/musl selection must detect libc without executing an arbitrary PATH tool.
The release graph is `native-host[seven targets] + validator-component → native-assemble → publish`. The existing tag-only publish job declares `needs: native-assemble`, downloads the assembled artifact and stages `dist/native/` before its existing publish allowlist/test/publish steps. Build tuples are `(windows-latest,x86_64-pc-windows-msvc)`, `(ubuntu-24.04,x86_64-unknown-linux-gnu)`, `(ubuntu-24.04-arm,aarch64-unknown-linux-gnu)`, matching Linux runners for the two `*-unknown-linux-musl` targets, `(macos-26-intel,x86_64-apple-darwin)`, `(macos-26,aarch64-apple-darwin)`; these labels are verified in [GitHub's hosted-runner documentation](https://docs.github.com/en/actions/reference/runners/github-hosted-runners). Each uploads `legion-wasi-host-<target>` containing only `legion-wasi-host[.exe]`, its hash and target/version/ABI metadata plus native smoke results. Musl executables must run in an Alpine container without GNU libraries. Assembly rejects missing/duplicate targets or inconsistent ABI/version, emits `legion-cli-native-host-manifest/v1` with sorted `{target,path,sha256,size}` entries, and uploads `legion-wasi-hosts`. Only the existing publish job publishes; it cannot race assembly. Native target checks are required for artifact production, while the existing general macOS sandbox leg remains best-effort. The separate guest build uses the pinned Rust toolchain/`wit-bindgen` 0.61.1 and must prove no unresolved host imports before the component is copied into the agents package resources.
Advertise native-host macOS support at macOS 26+ with a positive memory-limit enforcement probe; older macOS remains supported by the ordinary CLI, not this enhanced native boundary. GNU Linux builds require glibc 2.39+; build musl binaries statically and select them on musl or older GNU systems rather than pretend the Ubuntu 24 GNU binary loads everywhere. Linux-only libc selection uses the [Node 22 report](https://nodejs.org/docs/latest-v22.x/api/report.html) `process.report.getReport().header.glibcVersionRuntime`; temporarily exclude network reporting, retain only that header scalar and never log/persist the report's environment or other data. An unrecognized target, loader failure or non-enforcing kernel is a precise unavailable prerequisite, not an automatic PATH/download fallback. Root CI builds its local host/guest before required new native/consumer scenarios; workspace development may produce a local-target manifest, but publication requires the complete seven-target manifest. The guest ABI packet/header/result shapes and fixed budgets are versioned, and the SDK example exercises the same real component used in smoke.
Build the first-party guest as an import-free **`no_std` + `alloc`** Rust `cdylib` for `wasm32-unknown-unknown`, not a default WASI command whose panic/stdio machinery adds ambient imports. Pin [wit-bindgen 0.61.1](https://docs.rs/crate/wit-bindgen/0.61.1/features) with defaults off and only `macros,realloc`, [dlmalloc 0.2.14](https://docs.rs/crate/dlmalloc/0.2.14/features) with its `global` allocator, and [serde_json 1.0.145](https://docs.rs/crate/serde_json/1.0.145/features) with defaults off and `alloc`; use a trap-only panic handler, no randomized hash maps, and Cargo resolver 2. A proposed dev-only `packages/sandbox/native/pack-component/` builder uses [wit-component 0.258.3 `ComponentEncoder`](https://docs.rs/wit-component/0.258.3/wit_component/struct.ComponentEncoder.html) to encode the raw module and embedded WIT metadata with validation on and **no WASI adapter**. Commit these dependencies in the native workspace lockfile. Validate the final component against the empty host linker before packaging; a compile-only guest artifact is insufficient. The SDK documents this exact no-import build, rather than telling authors to link an ordinary WASI runtime.
Load TypeScript through a memoized dynamic import only when a knowledge binding is requested; new map exports must not eagerly import its parser. Likewise, optional host/controller/model/signing entry points remain inactive until their explicit feature path. Importing a workspace barrel or running legacy bare status must not initialize the native subsystem or model checker.

### 3. Make source-bound knowledge executable and evidence reuse sound
Add a proposed `packages/map/src/knowledge.ts` because existing regex import/export extraction cannot supply AST bindings. Add an exact `typescript@5.8.3` runtime dependency to map for TS/JS parsing. Resolve selectors by syntax kind and qualified lexical name; bind all declarations in a valid overload group, reject duplicate implementations/ambiguous scopes and report parse errors as `unknown`. Hash a normalized token/AST projection excluding positions/trivia but preserving operators, modifiers, literals and syntax order. Retain the full file-byte fingerprint separately; renames/deletions require an explicit manifest amendment. Other languages use whole-file byte bindings rather than a pretend AST engine.

The authored graph expresses requirement → knowledge unit → task/check → observation relationships. Its dependency edges are **declared semantics**, not proof of complete runtime reads. Build reverse impact queries from these relations plus observed input identities; existing map/wiki/graph surfaces remain discovery aids. Add advanced `plan evidence [--json]` and `plan impact [--json]` views for covered/failed/unknown criteria, changed bindings and the exact rerun/reuse reason. Do not auto-pass manual acceptance or invent a generic score from link counts.

Only the import-free component runtime qualifies for selective reuse. Each approved check receives exactly its declared file records, selected unit projections, explicit dependency-unit closure and configuration; its only observations are that input packet. Unit-projection inputs use normalized syntax, whereas `inputFiles` include raw bytes/mode/existence. No dependency inference can silently trim this packet. The host identity, OS/architecture, ABI, runtime settings, module digest, parser version, approved manifest digest, approval ID, check definition and exact canonical input digest form the reuse key. A prior **passed** check with identical key may be reused despite an unrelated product edit; every other result is rerun or remains explicitly blocked.

Persist proposed `.legion-cli/workflow/checks/<check-id>.yaml` receipts with schema version, check/approval/manifest IDs, input records/digest, module/runtime/parser/config identities, result, observation digest, execution ID and `reusedFrom` (null on execution). The corresponding proposed `.legion-cli/workflow/assurance-execution.yaml` summarizes the current global product/environment epoch, ordered required check references, policy/trace status and blocker. A cache hit is a referenced prior execution, not a fabricated fresh run. Perform before/after product checks around execution and reuse attachment; mutation or a source race invalidates the stage.

Integrate these checks into the existing task and focused integration pipelines through proposed `packages/core/src/assurance.ts`. Keep ordinary quoted `plan approve --check "command"` checks on their current whole-product/environment conservative rule: commands, dynamic imports, clocks, environment and network do not acquire selective reuse through an AST guess or write allowlist. Preserve the twelve-worker whole-product fingerprint and its complete tracked/untracked/non-Git path semantics.

Execute argv checks first in existing approved order, then component checks in manifest order, then independent review. Persist each completed check before starting the next. A current failed/unavailable check remains a concrete blocker without `--retry`; retry reruns the first failed component stage or the existing one failed argv/review stage, reuses prior eligible successes, and stops on another failure. Changed inputs invalidate a prior component failure's key and schedule a real new check, never turn it into a pass. A changed product always refreshes aggregate integration/review and manual-acceptance freshness even when some component checks are reusable. **Only assurance-adopted epochs** add the current assurance sidecar and trace gates to existing receipt/acceptance gates; non-adopted ship behavior is unchanged.

### 4. Enforce information flow with actual trusted-control separation
Implement a proposed `packages/http/src/governed.ts` interpreter selected only for an engine-owned assurance job. The current HTTP tool loop remains the unchanged non-adopted path. Extend `HttpAgentJob` with optional approved assurance context and a required effect-authorization host when that context is present; keep HTTP independent of core. Every adopted spawn/profile and recovery path must pass the same approved context. A vendor CLI/ACP cannot be upgraded by claiming it has a callback; refuse `information-flow` mode for those transports. Fake adapters are permitted only in explicit engine test fixtures, never as production evidence.

The privileged planner sees only human-approved spec/acceptance metadata, fixed task contracts, source/sink grants and named transformation instructions. It must **not** receive the existing assembled pointer prompt, repository/wiki/MCP text, quarantined output, raw error/log text or the old conversation. Before reading untrusted data it emits a bounded acyclic JSON program (at most 256 operations): `read` of a granted literal path, `derive` using earlier opaque value references and an approved transformation ID, `write` to a granted literal product/artifact path, `external-call` with fixed granted authority arguments/data-only references, and `finish`. Validate IDs, ordering, argument schema, destinations, resource limits and ownership before execution.
